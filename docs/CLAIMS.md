# Claim ledger: what is established, by which run, and what is open

Every row names the *shipped* code path that produced the number and the exact
command that regenerates it.  A claim without a matched measurement is listed as
open rather than estimated.  Latency numbers state their measurement window
because the GPU was shared while they were taken.

## B. Open questions

| # | open question | what is not established | the experiment that would establish it |
|---|---|---|---|
| B1 | 1M retrieval quality and 1M TPOT | No 1M measurement exists: a 1M bf16 Full-KV cache for Llama-3.2-1B is 32 GiB against 24 GiB of HBM, so the exact-prefill baseline cannot run at that length, and no 1M-native checkpoint is available. A7 measures length-independence up to the largest prompt that fits | Exact Full-KV prefill at 1M tokens on a device that holds a 32 GiB cache, then the same selection, decode and scoring path as the 128K rows |
| B2 | 128K TPOT >= 5x Full-KV | At 32K, with both arms CUDA-graphed, the parity-gated matched ratio is 4.9-5.0x (report 3.11b: bounded 11.01 ms vs Full-KV 53.7-55.2 ms, three repeats). At 128K the Full-KV arm OOMs on its own footprint with every execution path tried, so no matched 128K ratio exists; the bandwidth bound for a 1B model is 2.70x before weights are counted | `python benchmarks/benchmark_bounded_decode_tpot_floor.py --length 131072 --modes dynamic graph` on a device where the Full-KV arm fits, with the parity gate passing on both arms |
| B3 | Latency percentiles on exclusive hardware | Concurrent load on the shared GPU moves one bounded configuration between 6.9 and 18.4 ms per token, so only p50-style statements with a stated window are supportable | Re-run `benchmark_fullkv_tpot_graph.py` and `benchmark_bounded_decode_tpot_floor.py` on an idle GPU with repeats and report p50/p95/p99 |
| B4 | Finer int4 key quantization, and trained-compression baselines | With `--group-size 128` and a 64-wide head, the key axis uses a single scale per (layer, kv-head), the coarsest KIVI configuration, so the int4 loss in A14 is a property of this configuration rather than of int4; no learned eviction or trained-compression policy has been measured at matched bytes | Per-token or per-channel key scales, and a trained eviction policy, both evaluated at the byte counts in A14 |
| B5 | Bounded prefill transient memory | Retained decode state is bounded, but the exact chunked prefill still holds the prompt's full KV until the compile step, which is `O(L)` for one request | A prefill that keeps a bounded or host-resident KV while producing the same selected slot sets, verified against the current compile on the same records |

## C. What is deliberately not claimed

* That the retention law is a general-purpose attention approximation: it is a
  cache policy, and its quality is task-family dependent (§3.12).
* That language-modelling perplexity is preserved: bounded retention costs NLL
  relative to Full-KV (§3.10), while the retrieval-style tasks above are at
  parity.
* That the RULER retention figure transfers to arbitrary long-context tasks
  without the LongBench run (A13).
* Any 1M number: the state-growth argument is structural plus measured up to the
  largest length the measurement GPU can prefill, and says so.
